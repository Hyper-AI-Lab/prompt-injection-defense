# Release runbook

How a known-good `main` becomes an immutable, verifiable `containment` release.
One script drives the cut: `scripts/cut_release.sh`. One workflow builds and attests
the distributions: `.github/workflows/publish.yml`.

Current distribution channel: **GitHub Releases** (wheel + sdist with GitHub artifact
attestations). PyPI publishing is wired but **disabled** until the one-time setup in
[PyPI Trusted Publishing](#pypi-trusted-publishing-optional) is done. The package is not
on PyPI today; do not install `containment` from PyPI expecting this project.

## What a release contains

| Item | Source |
| --- | --- |
| Annotated tag `vX.Y.Z` | `cut_release.sh --execute`, on the commit where `pyproject.toml` and `containment.__version__` equal `X.Y.Z` |
| Release notes | The `## [X.Y.Z]` section of `CHANGELOG.md`, extracted verbatim |
| `containment-X.Y.Z-py3-none-any.whl`, `containment-X.Y.Z.tar.gz` | Built once by the `build` job of `publish.yml` on the tag, attested with `actions/attest`, downloaded and verified by the script, then attached |
| `eval-card.md`, `eval-card.json` | `containment-eval-card --suite fixtures` run by the script on the release commit |

## Preflight (every release)

1. `main` is green in CI and local `HEAD` equals `origin/main`.
2. Bump the version in **both** `pyproject.toml` (`version = "X.Y.Z"`) and
   `src/containment/__init__.py` (`__version__ = "X.Y.Z"`).
3. In `CHANGELOG.md`, rename `## [Unreleased]` content into `## [X.Y.Z] - YYYY-MM-DD`,
   leave an empty `## [Unreleased]` above it, and add the compare link at the bottom.
4. Commit (`Release containment X.Y.Z — <summary>`) and push to `origin/main`. Wait for CI.

## Cut

Dry run (default; changes nothing, safe to repeat):

```bash
scripts/cut_release.sh X.Y.Z
```

The script fails closed, in this order, and exits non-zero on the first failure:

1. `X.Y.Z` is not a plain `MAJOR.MINOR.PATCH` version.
2. `pyproject.toml` or `containment.__version__` differ from `X.Y.Z`.
3. `CHANGELOG.md` has no non-empty `## [X.Y.Z]` section.
4. Tag `vX.Y.Z` already exists locally.
5. Working tree is dirty (tracked or untracked files).
6. `HEAD` is not `origin/main`, or tag `vX.Y.Z` already exists on `origin`.
7. `scripts/release_gate.sh` fails (ruff, pytest, policy-ON eval, unfinished-marker scan).
8. `containment-eval-card --suite fixtures` reports `gate=FAIL`
   (`on_asr_ok`: ON ASR == 0.0000; `control_ok`: OFF ASR > ON ASR).
9. `python -m build` fails locally.

On success the dry run prints the exact commands `--execute` would run.

Execute (needs `gh auth status` OK with push rights):

```bash
scripts/cut_release.sh X.Y.Z --execute
```

`--execute` repeats every check, then:

1. Creates annotated tag `vX.Y.Z` (`containment X.Y.Z`) and pushes it to `origin`.
2. Waits for the `publish` workflow run on that tag and requires it to succeed.
3. Downloads the run's `dist` artifact and runs `gh attestation verify` on each file, bound to
   the tag (`--source-ref refs/tags/vX.Y.Z`) and to the signing workflow
   (`--signer-workflow Hyper-AI-Lab/prompt-injection-defense/.github/workflows/publish.yml`).
4. Runs `gh release create vX.Y.Z --verify-tag --notes-file <CHANGELOG section>` with the
   verified wheel + sdist and the eval card attached.

If step 2 or 3 fails, the tag exists but no GitHub Release is created. Fix the cause, then
delete the remote and local tag (`git push origin :refs/tags/vX.Y.Z && git tag -d vX.Y.Z`)
before re-running; never re-point a published tag.

## Publish workflow

`.github/workflows/publish.yml` triggers on `push` of tags `v*` (and `workflow_dispatch`
for a build-only check from `main`).

- **build** (always): checkout, Python 3.12, assert tag version == `pyproject.toml` version
  (tag runs only), `python -m build`, `twine check --strict`, `actions/attest` build
  provenance for `dist/*`, upload `dist` artifact. Permissions: `contents: read`,
  `id-token: write`, `attestations: write`.
- **publish** (PyPI): runs only on a tag **and** when repository variable
  `PYPI_PUBLISH` is `true`. Downloads the same `dist` artifact (no rebuild) and uploads
  with `pypa/gh-action-pypi-publish@release/v1` through Trusted Publishing; PEP 740
  attestations are generated by that action. Environment `pypi`; permission
  `id-token: write` only. No API tokens are stored anywhere.

With `PYPI_PUBLISH` unset the publish job shows as **skipped** and the run is green.

## Verify a release (consumers)

```bash
gh release download vX.Y.Z -R Hyper-AI-Lab/prompt-injection-defense -p 'containment-*'
gh attestation verify containment-X.Y.Z-py3-none-any.whl -R Hyper-AI-Lab/prompt-injection-defense \
  --source-ref refs/tags/vX.Y.Z
gh attestation verify containment-X.Y.Z.tar.gz -R Hyper-AI-Lab/prompt-injection-defense \
  --source-ref refs/tags/vX.Y.Z
pip install ./containment-X.Y.Z-py3-none-any.whl
containment --version
containment doctor --install-only
```

`--source-ref` rejects attestations from builds of other refs (for example a
`workflow_dispatch` build on `main`). Needs gh 2.49 or newer.

Or install straight from the tag (no attestation check):

```bash
pip install "git+https://github.com/Hyper-AI-Lab/prompt-injection-defense.git@vX.Y.Z"
```

## PyPI Trusted Publishing (optional)

Gate G0, done once by the PyPI account owner. Until then nothing is uploaded to PyPI.

1. On PyPI, open *Your projects → Publishing → Add a new pending publisher* (or the
   project's *Publishing* page if `containment` already exists under your account) with:
   - PyPI project name: `containment`
   - Owner: `Hyper-AI-Lab`
   - Repository: `prompt-injection-defense`
   - Workflow name: `publish.yml`
   - Environment name: `pypi`
2. On GitHub, *Settings → Environments → New environment* `pypi`. Recommended: add
   required reviewers and restrict deployment to tags matching `v*`.
3. On GitHub, *Settings → Secrets and variables → Actions → Variables*, add repository
   variable `PYPI_PUBLISH` = `true` (CLI: `gh variable set PYPI_PUBLISH --body true`).
4. Next tag push publishes. Verify at `https://pypi.org/project/containment/` and confirm
   the files show provenance on their PyPI file pages.

To upload a version that was tagged while PyPI was disabled (from `v1.7.0` on), open
*Actions → publish → Run workflow*, choose the tag `vX.Y.Z` under *Use workflow from*, and
run it after step 3. PyPI rejects files it already has, so this is safe to retry.

## History

Versions 1.0.0–1.6.1 were released as commits on `main` (`Release containment X.Y.Z`).
Their annotated tags were backfilled on those exact commits in 1.7.0; they have no
GitHub Release objects. `v1.7.0` is the first release cut with this runbook.
